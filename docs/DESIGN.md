## 1. 姿态解算的本质数学公式

### 1.1 与底盘公式的类比

底盘：`Wheels = J·(vx, vy, ωz)ᵀ` —— 静态代数映射，无记忆无积分。
姿态：**积分量**，本质是"微分方程 + 反馈修正律"（观测器），不是静态矩阵。

### 1.2 本质公式（所有算法的通用形式）

```
（1）过程模型（唯一、固定、与算法无关）：
     q̇ = ½ · q ⊗ (ω_meas − b)        ḃ ≈ 0
     矩阵形式：q̇ = ½·Ω(ω)·q

（2）观测模型（量测来源，可插拔）：
     z = h(q) = R(q)ᵀ · v_ref
     —— 加速度计：v_ref = g（重力矢量，定 roll/pitch）
     —— 磁力计  ：v_ref = m（地磁矢量，定 yaw）
     —— 外部参考：v_ref = 编码器/里程计/视觉给的航向

（3）修正律（算法的全部差异集中在这里）：
     q̂̇ = ½·q̂⊗(ω−b̂) + K · (z − h(q̂))          ← 本质公式
     b̂̇ = 增益律（Mahony 的 Ki·∫err / EKF 的状态更新）
```

- `z − h(q̂)` 是残差（实测重力方向 vs 预测重力方向的夹角）；
- `K` 是增益：Mahony=Kp 常数（叉积误差）、Madgwick=β 梯度步长、EKF=P⁻Hᵀ(HP⁻Hᵀ+R)⁻¹ 时变最优；
- **Kalman 与 Mahony 不是两类东西，是同一观测器方程下 K 的两种求法。**

### 1.3 为什么姿态没有静态公式

同一帧 (ω, a) 对应无穷多姿态历史 —— 姿态是微分方程的解，必须做成带记忆的状态估计器。

### 1.4 特例：2D 退化（gyro-z 小车方案 = 本质公式的一维退化）

```
预测：ψ̇ = ωz          （只积分 z 轴）
观测：ψ_ref（可选）
修正：ψ̂̇ = ωz + K·(ψ_ref − ψ̂)
K=0 → 纯陀螺积分（现状）；K>0 → 互补/一维 Kalman
```

三维公式与一维公式**数学结构完全同构** —— "一个核心覆盖 2D/3D"在公式层面成立。

### 1.5 姿态表示选型

| 表示 | 优点 | 致命缺点 |
|---|---|---|
| 欧拉角 | 直观、与云台轴系对应 | 万向锁；微分方程复杂 |
| 方向余弦矩阵 | 无奇异 | 9 参数 + 必须正交化 |
| **四元数** | 无奇异、4 参数、微分方程最简、计算最快 | 不直观；须归一化 |
| SO(3) 李群 | 理论最优雅 | 实现复杂，MCU 少见 |

四元数归一化是积分后必须做的一步；欧拉角只在**输出层**转换。

### 1.6 本质公式对架构的推导

```
predict(gyro, dt)                     —— 唯一固定的运动学
observe_vector(vec, ref, trust)       —— 6轴/9轴向量观测
observe_heading(heading_ref, trust)           —— 外部航向注入
correct()                             —— 增益求解器可插拔（算法差异只在这里）
```

## 2. 场景覆盖与产品分析

### 2.1 三个场景的真实需求

| 需求维度 | 地面寻迹小车 | 云台 | 立体步兵 |
|---|---|---|---|
| 自由度 | 1（yaw） | 2~3 | 3（地形冲击大） |
| 核心量测 | 陀螺 z 积分 | 三轴陀螺+加速度计(+磁) | 三轴陀螺+加速度计(+视觉) |
| 动态范围 | 低 | 高（1000°/s 量级） | 极高（弹道冲击） |
| 更新率 | 100~200Hz | 500Hz~1kHz | 500Hz~1kHz |
| 主要矛盾 | 零偏累积 | 动态跟随 vs 噪声 | 运动加速度污染量测 + 冲击后快速恢复 |

**三个场景运动学完全相同，差的是传感器配置与量测可用性 → "一个核心 + 配置档位"可行。**

### 2.2 关键约束①：可观测性（决定"通用"的天花板）

- 只用 6 轴 IMU，**绝对 yaw 永远不可观**（重力与 yaw 旋转轴平行）；yaw 只能靠陀螺积分（相对航向）；
- 参考库明证：`GyroBias[2]=0`（z 轴零偏不估）+ q3 修正强制置零；
- yaw 绝对参考只能来自外部（磁/GPS/视觉/编码器/里程计）→ **核心必须留"外部 yaw 参考注入"接口**；
- 加速度计在非静止/非匀速时不可信 → 6 轴精度上限取决于"量测仲裁"（静止检测+拒收）做得多好。

### 2.3 关键约束②：维度降级（2D ≠ 3D 的特例那么简单）

- 2D 模型：`ψ̇=ωz`；3D 模型：`q̇=½Ωq`；
- **陷阱**：把 3D 核心跑在小车上（ωx=ωy≈0），x/y 轴零偏与振动被积分 → roll/pitch 漂移 → 四元数归一化耦合污染 yaw；加速度计修正还会把振动当真拉回来；
- **必须显式支持降维模式**（见 §3.5），而不是靠"喂零值"隐式降维。

### 2.4 结论：一套核心全覆盖 —— 可行，但是"平台 + 模式"

```
┌─────────────────────────────────────────────────┐
│            通用姿态核心（与场景无关）               │
│  状态模型：四元数(+零偏) 或 单轴 yaw 模式           │
│  预测：   q̂̇ = ½·q̂⊗(ω−b̂)     （唯一固定部分）    │
│  修正：   K·(z − h(q̂))                           │
│  ┌─ 可插拔增益求解器 ─┐   ┌─ 可插拔量测源 ──────┐  │
│  │ Mahony / Madgwick │   │ 加速度计(6轴)       │  │
│  │ EKF / 单轴KF      │   │ 磁力计(9轴)         │  │
│  └──────────────────┘   │ 外部yaw参考(编码器/  │  │
│                         │ 里程计/GPS/视觉)    │  │
│  └──────────────────────┴─────────────────────┘  │
│  保护机制：静止检测 / 卡方检验 / 自适应增益 / 限幅   │
└─────────────────────────────────────────────────┘
        │                    │                    │
   profile: yaw-only    profile: gimbal      profile: infantry
```

### 2.5 产品分析

**市场空位**：现有开源库里没有"一个内核、多算法插拔、2D/3D 模式、跨平台纯 C++、零依赖"的组合档位：
- x-io 最干净但单算法；PX4 ECL 最全但为无人机定位场景设计、移植成本极高；6-Axis-AHRS 接近但写死 RoboMaster 场景；参考库绑定 STM32+ARM DSP。

**差异化定位**：姿态解算界的"可移植数学内核"（类比 CMSIS-DSP 之于数字信号处理）：
- 纯 C++17 / 零动态内存 / 无 OS 依赖 / header-only 可编译；算法可插拔；维度模式 + 量测源配置；平台层只留 3 个钩子（时间戳、数学函数、日志）。

**风险清单**：① 可观测性天花板（宣传须诚实：绝对航向需外部参考）；② 验证成本高（需数据集+真值+转台）；③ EKF 调参门坎（需 Allan 方差工具+默认参数）；④ 与闭源商业库（MotionFX）的竞争取决于生态与口碑。

## 3. 设计决策记录（含 C++ 构建等问答结论）

### 3.1 C++ 构建影响（已定：C++17）

| C++ 特性 | 用途 | 嵌入式纪律 |
|---|---|---|
| class + 句柄式实例 | 消灭全局单例 | 允许，核心价值 |
| 模板（Scalar float/double、DoF） | 一处实现双精度/单精度、2D/3D 复用 | 允许，零开销 |
| 运算符重载（四元数） | 数学表达贴近公式 | 允许，注意内联无临时对象 |
| 虚函数/策略模式 | 算法可插拔 | 允许，1kHz 下每帧几 ns 可忽略 |
| STL | — | **默认禁用**，或提供 FOULCAULT_NO_STL 开关 |
| 异常/RTTI/动态内存 | — | **禁用**（-fno-exceptions -fno-rtti，零 malloc） |
| if constexpr / constexpr 配置 | 编译期裁剪 | 允许，替代 C 宏 |

### 3.2 六轴 vs 九轴（设计结论：量测源配置差异，非架构差异）

| | 6 轴 | 9 轴 |
|---|---|---|
| roll/pitch | 可观 | 可观 |
| yaw | **不可观**（积分漂移） | 可观（地磁定航向，需校准） |
| 动态可靠性 | 加速度计被运动加速度污染 | 磁力计受电机磁场/铁磁体干扰 |
| 附加成本 | 无 | 椭球/软硬磁校准 + 干扰检测 |

**对核心的 5 个影响**：① 状态向量不同（9 轴可把磁场放进 EKF 状态在线估计）；② yaw 处理策略不同（6 轴=外部注入接口+接受漂移；9 轴=磁观测）；③ 磁力计需要自己的可信度仲裁（模长/倾角/残差门限）；④ 校准管线是独立模块（坏磁数据比没磁更糟）；⑤ 计算量差异可忽略。

**场景选型**：小车 = 6 轴 + 里程计 yaw；云台 = 6 或 9 轴可选；步兵 = 6 轴为主（全金属+大电流电机，磁力计实测报废）+ 视觉可选。

### 3.3 外部 yaw 真相源清单

**产品传感器配置（2026-08-30 用户确认）**：里程计 **确定有**；视觉 **待定**；磁力计 **大概率没有**。→ 后续设计以"6 轴 + 外部 yaw 注入"为主线：yaw 真相源 = 轮式里程计（地面小车）/ 云台编码器 / 视觉（若上）；9 轴磁力计方案降为可选分支，优先级降低。

| 来源 | 原理 | 精度/频率 | 可用条件 | 适用场景 |
|---|---|---|---|---|
| 磁力计 | 地磁水平分量 | 1~5°（校准后） | 无强磁场干扰、需椭球校准 | 云台、室外车 |
| 轮式里程计 | 左右轮速差积分 | 短时好，打滑发散 | 地面无打滑 | 地面小车首选 |
| 云台/关节编码器 | 电机编码器 | 0.1° 级 | 有固定基座参考 | 云台相对 yaw |
| GPS 航迹/速度方向 | 对地速度矢量 | 需速度 >2~3m/s | 室外开阔、运动中 | 室外车、无人机 |
| RTK 双天线 | 载波相位差 | 0.1~0.3° | 室外、贵 | 无人车/农机 |
| 视觉（AprilTag/VIO） | 视觉定位航向 | 0.1~1° | 有纹理/标签 | RM 步兵、室内车 |
| 光纤/激光陀螺 | 感知地球自转 | 0.01°/h 级 | 成本 >1 万元/轴 | 舰船/导弹，MEMS 不可行 |

**接口含义**：`observe_heading(heading_ref, trust)` 一等公民；多源可同时注入（EKF 天然支持多量测）；无真相源时优雅降级为纯积分并标注"相对航向"。

### 3.4 多算法可插拔（已定：可行）

- 理论依据：本质公式中算法差异只在 K；
- 例证：gaochq 一框架三算法、Library-SensorFusion 四算法、PX4 的 attitude_estimator_q 与 EKF2 并存；
- 实现：运行期策略（虚函数，推荐）或编译期策略（模板，零开销但运行期不可换）；
- **三条铁律**：① 数学内核共享不插拔；② 插拔分两层：状态模型层（2D/3D，模板 DoF）> 增益求解器层（Mahony/EKF/KF）；③ 每个可插拔件携带自己的配置与状态（对象/结构体，不是裸函数指针）。

### 3.5 显式降维（Explicit Dimension Reduction）

**定义**：核心主动把状态模型裁剪到应用的真实自由度，而非靠"喂零值"隐式实现。

2D 完整退化：`预测 ψ̇=ωz / 观测 ψ_ref / 修正 ψ̂̇=ωz+K(ψ_ref−ψ̂)`。

**为什么必须显式**（隐式降维的坑）：把 3D 核心跑 2D 平台 → ① x/y 零偏与振动被积分，roll/pitch 漂移；② 四元数归一化耦合污染 yaw；③ 加速度计修正把振动当真拉回来；④ 调参无物理意义。显式降维在模型层解决：状态只有 ψ，从根上消除无效自由度。

**2.5D 中间形态**：3D 状态 + roll/pitch 量测降权或限幅（云台底座/步兵地形感知场景的档位）—— 不是 2D 也不是满 3D。

### 3.6 可插拔契约：三层模型（⏳ 提案，待用户确认后生效）

**问题起因（2026-09-11 代码审阅）**：批次 3 完成后发现 `predict` 的语义在 Mahony（修正折进 ω，predict ≡ 外推+修正）与 EKF（predict = 纯外推，修正单独在 update）之间存在歧义，由此引出质疑：
> "一体通用库的可插拔是不是巧合？本质不同的解算方式是不是不同的路径？"

**判定：可插拔成立，但抽象层必须画在"数据进 / 结果出"，而不是"算法内部步骤"。**

#### 3.6.1 存在性证明：参考库三算法同一接口

`reference/IMU_Attitude_Estimator` 已跑通"一个框架三种算法"：

```cpp
Eigen::Quaterniond Run(Vector_9 measurement);   // include/EKF_Attitude.h:49
Eigen::Quaterniond Run(Vector_9 measurement);   // include/ESKF_Attitude.h:53
Eigen::Quaterniond Run(Vector_9 measurement);   // include/Mahony_Attitude.h:29
```

同时暴露一个**共通泄漏**：三个构造函数签名完全不同（`bool+dt` / `Vector2d+dt` / `Vector12+dt`）——**配置层无法统一**，与本项目 P0-1（config 硬编码）同病。

#### 3.6.2 关键澄清：predict/observe 是"世界的节奏"，不是"算法的结构"

| 论据 | 内容 |
|---|---|
| 需求来自输入侧 | 陀螺 1kHz / 加速度计 100Hz / 外部 yaw 10Hz —— **速率不同 → API 必须允许分开喂**（F4）。即使世界上没有 EKF，这个划分仍然需要 |
| EKF 同名是巧合 | 算法内部也叫 predict/update，但契约层的 predict/observe 与该命名**无依赖关系** |
| 代价已知 | 参考库 `Run(整帧)` 抽象更粗 → **丧失异步多速率能力**；本项目选择更细的抽象（能力更强），代价是更容易与实现层贴合 |

**为什么 `observe` 不叫 `correct`（2026-09-12 定案）**：

| 论据 | 内容 |
|---|---|
| **最硬的一条：修完 P0-4 后，`observe` 可以发生而修正不发生** | 加速度计断线时 `observe` 仍在被调用（存残差、算 `v̂`），但 `predict` 里 `has_valid_acc() == false` → **不修正**。若叫 `correct()`，就是**名字撒谎** |
| 契约层描述"世界发生了什么"，不描述"我内部做了什么" | `observe(z)` = 「一个量测到来了」（**外部事件**）；`correct()` = 「我执行了修正」（**内部动作**）|
| `correct()` 会泄漏实现假设 | 它隐含"存在一个独立的修正步"——那是**实现层**的事：**Mahony 把修正折进 `predict`**，只有 EKF 才有独立修正步。契约层若叫 correct，Mahony 的实现会变成"correct 里只存残差、不修正" → 再次撒谎 |
| 与 `predict` 对称，构成"世界的节奏" | `predict(dt)` = 时间流逝了；`observe(z)` = 量测到来了。**两者都是外部事件** |
| 历史 | `§1.6` 早期草案承诺过 `correct()`，**从未落地**（见 F14），因为 Mahony 拆不出独立修正步 |
| `observe` ≠ 一定会用 | `trust = 0` / solver 不支持该量测（F14 能力层）/ `age` 过期 —— 三种情况都是"观察到了但不信它" |

**术语落位（四层，勿混用）**：

```
纠正计           数据源的角色（外部概念："我能提供航向 / 重力方向"）
   ↓
observe(_yaw)    契约层：一个【观测】到来了（不管用不用、信不信）
   ↓
predict          契约层：时间推进（含该求解器自身的修正机制）
   ↓
correct          实现层专用词：Mahony 没有此步；EKF 有
```

#### 3.6.3 三层模型

```
┌─ 契约层（算法无关，所有求解器必须满足）────────────────────────┐
│  输入节奏:  predict(gyro, dt) 高频 / observe(量测, dt) 低频       │
│  状态提交:  quaternion() / euler()                                │
│  生命周期:  reset() / reset(Quatf)                                │
│  品质输出:  status() → 收敛? / 绝对or相对航向? / 降级?   ← F8 待实现 │
├─ 能力层（算法特定，必须显式声明"支持/不支持"）─────────────────┤
│  trust 权重 / observe_heading / observe_mag / bias_estimate / covariance │
├─ 实现层（完全不透出）────────────────────────────────────┤
│  Mahony:  修正折进 ω → predict ≡ predict + correct 一体                │
│  EKF:     predict（状态+协方差传播）→ update（增益+修正）显式两步        │
└──────────────────────────────────────────────────────────┘
```

**术语定义（待写入 `core/estimator.hpp` 头注释，见 P2-8）**：

```
门面 predict 的语义 = 时间推进（time update），**含该求解器自身的修正机制**；
                      不是"纯外推"。
门面 observe 的语义 = 量测更新（measurement update）。
```

#### 3.6.5 提案修法（三条，不推翻架构）

① **补 `trust` 通道**：`observe(s, dt, trust = 1.0f)`，默认参数向后兼容。EKF → R；Mahony → 乘在残差上（`ω += Kp·trust·e`，物理意义：不太可信的量测修正力度就小）。

② **加能力查询**（编译期，零开销，合 F13）：

```cpp
template <typename S> struct solver_traits;
template <> struct solver_traits<solver::Mahony> {
    static constexpr bool supports_external_heading = false;   // 批次 4a 后改 true
    static constexpr bool supports_trust_weight = true;
    static constexpr bool has_bias_estimate     = true;
};
```

→ 把"静默丢弃"变成"**可查询地丢弃**"。

③ **补品质输出（F8）**：调用方最需要知道的不是"内部用了哪种矩阵"，而是"**这个估计现在能不能信**"：

```cpp
struct OutputStatus {
    bool  is_converged_;      // 收敛了吗
    bool  is_heading_absolute_;   // 航向绝对/相对（6 轴下恒 false）
    bool  is_degraded_;       // 观测源失效降级了吗
    float innovation_;        // 残差监控值
};
```

→ 落地后"`observe_heading` 被静默忽略"这个陷阱自动消失（读 `is_heading_absolute_` 即知）。

④ **把 `is_meas_` 布尔闩锁换成残差年龄计数器**（2026-09-12 实测发现，P0-4）：

现状 `mahony.cpp:25` 的门禁只判"**是否收到过**量测"（`mahony.cpp:51` 一次置位、除非 reset 永不回退），**无时效检查**。后果：量测中途失效时残差被冻结，`ω += Kp·e_last_frozen` 退化为**恒定假角速度**（≈ Kp·|e| ≈ 14 °/s），且 `q̂ → v → e` 反馈环断开 → 无负反馈 → 姿态匀逐跑飞。实测（第 100 s 断加速度计，后 220 s 无修正）：

| 方案 | 失效后 RMSE | 峰值 | 恶化到 >10° 用时 |
|---|---|---|---|
| 正确降级（纯陀螺） | 5.468° | 13.738° | 198.6 s |
| **现状代码** | **117.582°** | **185.169°** | **1.48 s** |

修法：不存"是否收到过"，存"**距上次有效量测多久**"——一个状态同时覆盖启动与失效：

```
float age_ = INF;                     // 初始=从未收到
observe(): age_ = 0;                  // 收到就重置
predict(): age_ += dt;                // 每次推进累加
           if (age_ < timeout_) 修正
           else                 纯陀螺 + 置 is_degraded_
```

| 情形 | `age_` | 行为 |
|---|---|---|
| 启动，从未收到 | `INF` | 不修正（原 `is_meas_` 语义）|
| 正常 | `< timeout` | 正常修正 |
| **中途失效** | `> timeout` | **自动回退纯陀螺**（不再跑飞）|

→ 即 `age_` **严格包含**了布尔闩锁的职能，而后者无法覆盖失效场景。`timeout_` 合理量级：量测周期的 5~10 倍（100 Hz 加速度计 → 50~100 ms）。
→ 由此三件套改为：**① `trust`（传参）+ ② `residual age`（状态，吸收旧 `is_meas_`）+ ③ `is_degraded_`（输出标志，通知调用方）**。

⑤ **`Quat::normalize` 不得吞掉 NaN**（2026-09-12 core/math 独立审计发现，P0-5；**✅ 已落地**）：

`quat.hpp:29` 的守卫 `if (n2 > T(0))` 在 `n2` 为 NaN 时比较恒为 false → 静默 `*this = identity()`。后果（solver 层实测）：单帧 `acc=NaN` → `e_int_` 永久 NaN → `ω` 恒 NaN → `q` 每帧被重置为单位元 → **姿态突变到水平朝北且永久卡死，无任何错误信号**（即使之后 1 万帧数据全正常）。

```
// 修前（会吞 NaN）                       // 已落地（只区分零与脏）
if (n2 > T(0)) { 缩放 }                  if (n2 > T(0))       { 缩放 }
else { *this = identity(); }             else if (n2 == T(0)) { *this = identity(); }
                                         // NaN 不处理 → 脏值传播到调用方可见
                                         // （+Inf 仍走 if 分支，结果非有限、可检出）
```

→ 原则：**防御机制只应对付它真正认识的那一种输入**（零四元数）；对不认识的值（NaN/Inf）应当**传播而不是掩盖**（合 AGENT.md“不静默吞错”）。
→ `+Inf` 输入走的是另一分支（`inf > 0` 为 true）→ 得到 `(inf, nan, nan, nan)`，同样无定义域检查。
→ 测试锚点：`tests/unit/test_math_audit.cpp` G2a/G2b。

### 3.7 外部 yaw 注入（批次 4a）：内部逻辑 ⏳ 提案待确认

> 承接 §3.3（yaw 真相源清单）、§3.6（可插拔契约）。原稿见 `HANDOFF.md §6`（2026-08-30），**本节为更新版**：已吸收 P0-4（禁布尔闩锁）、P0-5、F14（trust 通道）的结论。

#### 3.7.1 为什么需要它（物理）

六轴（acc + gyro）下 **yaw 完全不可观**：重力向量绕世界 z 轴旋转不变 → 加速度计对 yaw 是"瞎"的。

```
实测（NAV2 320s@50Hz）：roll RMSE 2.15° / pitch RMSE 2.65°  ← 被重力拉住了
                        yaw 漂移 −14.5°                     ← 没人管，陀螺零偏自由积分
```

roll/pitch 有真相源（重力），**yaw 没有**。要么接受漂移并对外声明"这是相对航向"，要么注入外部参考（§3.3 清单：里程计 / 磁力计 / 视觉 / 编码器）。

#### 3.7.2 修正量往哪加（数学）—— 本节最关键的一条

三个候选，只有一个对：

| | 方案 | 公式 | 后果 |
|---|---|---|---|
| ❌ | 加**机体系** z 轴 | `ω += Kp_heading·e_heading·(0,0,1)` | 机体水平时"碰巧"对；**一旦有 roll/pitch（斜坡、机动），绕机体系 z 转 ≠ 绕重力轴转** → yaw 误差泄漏成 roll/pitch 误差 |
| ❌ | 直接改四元数 | `q ← q ⊗ from_euler(0,0,e_heading)` | 绕过 `predict`/`integrate`，破坏"所有修正都折进 ω"的架构（§3.6），且后续换 EKF 时全部作废 |
| ✅ | **沿重力方向加** | `ω += Kp_heading·e_heading·v̂`，`v̂ = q*·(0,0,1)` | 绕**世界 z 轴**转 = 纯 yaw 修正，与 roll/pitch 解耦 |

`v̂ = q̂*·(0,0,1)` 是**纯状态投影，不需要任何量测** —— 所以批次 4a 的实现在 `predict` 里**用当前 `q_` 现算**，而**不**把它提升为成员。

> **这是相对早期草稿的改进**（2026-09-12 实测确认）：若把 `v_` 存成"最近一次 `observe` 时算的值"，那么在 `observe` 不运行的周期里 `v_` 会变旧 —— 更糟的是，**航向通道会因此依赖 acc 通道**（acc 断线 → `v_` 不刷新 → yaw 修正轴变歪）。
> 现算的代价是每个 `predict` 多一次四元数旋转（≈30 flops，1kHz 下 < 0.01% CPU），换来的是**两个通道在实现层面也完全解耦**。

**为什么 `v̂` 是对的**：它是"世界 z 轴在机体系里的表达"。在机体系里沿 `v̂` 施加角速度 ≡ 在世界系里绕 z 轴转 ✓。它和 `e_last_` 出自同一次 `observe`，**时间基准天然一致**。

**为什么只有 `v̂` 方向可行（数学证明）**：

```
e_acc = a × v̂        ⇒  e_acc ⊥ v̂        （叉积必垂直于两个乘数）
⇒ ω_acc · v̂ = 0                          （沿重力轴的分量为零）
⇒ 加速度计通道对 yaw 的贡献【恒为零】
```

这是**结构性失明**，不是"调得好不好"的问题。于是两个通道天然正交：

| 通道 | 负责的自由度 | 为什么管不了别人 |
|---|---|---|
| acc | 倾斜（roll / pitch）| `e ⊥ v̂` ⇒ 转不到重力轴上去 |
| yaw | **绕重力轴的角度** | 只沿 `v̂` 加 ⇒ 只动 yaw |

**两个推论**：
- yaw 通道**不是在修补 acc 通道的 yaw 误差**，而是**填补一个数学上无人负责的自由度**；
- **动态加速度污染只污染 roll/pitch**（实测见 §3.8.1），yaw 的污染源**只有陀螺零偏一条**。

#### 3.7.3 残差怎么算（数学）

```
e_heading = wrap(ψ_ref + heading_offset_ − ψ_est)      ← 必须 wrap，否则 179°/−179° 算出 358° 猛转
e_heading = clamp(e_heading, −π/2, +π/2)               ← 防大跳变（视觉误识别 / 里程计跳变）
```

- **`heading_offset_`（首次观测自动对齐）**：估计器初始 yaw 是任意的（从 identity 起步 = 0°），参考却可能是 37°。首次观测记下 `heading_offset_ = ψ_est − ψ_ref`，之后只跟踪**变化量** → 任意初始航向都能对上，无需手工对准。
- `reset()` 后必须**重新对齐**，否则旧 offset 会把新姿态拉偏。

**时序澄清（`mahony.cpp:56-59` 为证）**：一个 `update()` = `observe` → `predict`，即一个完整周期内完成"量测→残差→修正+推进"。但 `observe` 里算 `v̂` 用的 `q_` 是**本周期修正前**的状态：

```
q_k ──observe: v̂ = q_k*·(0,0,1), e = a × v̂──► e_last_
     ──predict: ω = gyro + Kp·e_last_ + Ki·e_int_──► integrate ──► q_{k+1}
```

`v̂` 与 `e` 出自**同一个** `q_k`，它们生成的修正产出 `q_{k+1}` —— **残差永远比它修正的状态"晚一步"，而这正是对的**（不能用还没处理的信息去修正），且保证修正**恰好被施加一次**、不重复计数。

**多速率下的直接后果**：若 yaw 参考 10Hz、`predict` 50Hz，则

| 做法 | 后果 |
|---|---|
| ❌ 只在收到参考时算一次 `e_heading_`，之后 5 个周期复用 | 残差不随 `q̂` 收敛而更新 → 修正变成"死值保持" → **过冲/振荡** |
| ✅ 存**参考值**（`ψ_ref + offset`），**每周期用当前 `q̂` 重算 `e_heading`** | 等价于连续 P 控制器，一阶收敛 `τ = 1/Kp_heading` ✓ |

**⚠️ 行为陷阱（实现时实测踩到 3 次，必须写进 CODE.md）**：自动对齐意味着

```cpp
est.reset(Quatf::from_euler(0, 0, 0.2f));   // 当前 yaw = 0.2
est.observe_heading(1.0f);                      // 首次 → offset = 0.2−1.0 = −0.8
                                            // 目标 = 1.0 + (−0.8) = 0.2 = 当前值 → 残差 0，【不动】
```

**这是设计行为，不是 bug**（参考的起源是任意的，只跟踪变化量）。想让 yaw 收敛到某值，必须**从当前 yaw 出发斜坡过去**，或先 `reset(目标姿态)` 再注入。

→ 由此定案：`observe_heading(heading_ref, trust)`，**不带 `dt`**（修正折进 `predict` 的 ω，`dt` 由 `predict` 提供；"保持参考值"方案用不到它，**不留死参数**）。

**该原则推广到【所有通道】（2026-09-12 批次 4a-2 定案）**：

> **残差必须在 `predict` 里用【当前】`q̂` 现算，不得冻结。**
> 对应的结构即「**统一消费口**」：`observe*` 只收集量测（向量/标量），`predict` 是唯一的消费+推进点，`v̂` 每周期只算一次。

原结构只对航向通道这么做了，acc 通道仍是"`observe` 算好残差存 `e_last_`，`predict` 复用" → 于是 acc 通道藏着**同一个缺陷**：

| acc 速率（`predict` 固定 500Hz）| 冻结残差（旧）| 每周期现算（新）|
|---|---|---|
| 500 Hz | 0.1980 s | **0.1980 s** |
| 100 Hz | 0.1940 s | **0.1980 s** |
| 20 Hz | 0.1740 s（快 12% ✗）| **0.1980 s** |

（表中为从倾斜误差收敛到 1/e 的时间常数 τ；理论值 = 1/`Kp` = 0.2000 s，应与量测速率**无关**）

→ **冻结残差 = 等效增益随量测速率漂移**。IMU 的 acc ODR 常低于循环速率（如 acc 100Hz、循环 400Hz），这个缺陷平时看不出来但真实存在。
同速率（1:1）下两版**逐位相同** —— 修复不改变正常工况的行为，只消除多速率下的耦合。

**理论吻合点**（可预测而非调参）：恒定参考稳态误差 = 零偏/`Kp_heading` = **0.01 rad**（实测 0.0100）；斜坡跟随滞后 = 斜率×τ = **0.04 rad**（实测 0.0400）。

#### 3.7.8 决策（2026-09-12 定案：用户采纳下列推荐）

| # | 决策 | 定案 |
|---|---|---|
| Y1 | `kp_heading_` 起步值 | **5.0f**（回放标定） |
| Y2 | 残差限幅 | **`±π/2` 硬 clamp 先行**；验收④不达标再改软限 |
| Y3 | yaw 是否参与 `Ki` | **否**。定量依据：纯 P 的稳态误差 = 陀螺零偏 / `Kp_heading` = (0.5°/s)/(5) = **0.1°**，可忽略；而打滑污染积分器的风险远大于此 |
| Y4 | `trust` + `heading_age_` + 品质标志 | **一次做齐**（分两次必返工；品质标志对小车导航是**必需**） |
| Y5 | `observe_heading` 的 `dt` 形参 | **删除**（理由见 §3.7.3 多速率一节） |

### 3.8 量测仲裁层（概念定案，实现待批次 4b）

#### 3.8.1 为什么必须有：acc 污染实测（2026-09-12，NAV2 320s@50Hz）

用真值姿态算出"真重力在机体系的方向"，与实测 `acc` 方向比夹角 = **加速度计这一帧读错了多少度**：

| 指标 | 值 |
|---|---|
| 量测方向误差 均值 / 中位 / 90 分位 | **4.17°** / 4.35° / 5.83° |
| **峰值** | **31.39°** |
| 误差 > 5° 的帧占比 | **29.2%** |
| 输出 tilt 误差（roll/pitch 合成）| 2.40°（峰值 13.60°） |
| corr(量测污染, 输出误差) | +0.45 |

**★ 反直觉发现：朴素的"模长门控"几乎无效**

```
corr(|‖a‖−1| , 量测方向污染) = +0.115          ← 几乎无关
污染 > 5° 的 4675 帧中：|‖a‖−1| < 0.05 的占 72.2%（全部漏检）
```

**原因（几何）**：水平方向的线性加速度几乎不改变 `‖a‖`，却大幅改变它的**方向**：

```
0.1 g 水平加速度 → ‖a‖ 只变 0.0050（"看着很静止"）
                 → 方向却偏 5.7°（严重污染）
```

→ **门控判据必须建立在"方向/残差"上，绝不能建立在"模长"上。** 这是参考库要用卡方检验而非简单阈值的原因，也是本项目**直接跳过第 1 档（简单模长门控）**的实测依据。

> 另一条实测事实：即使最平静的 25% 帧，量测仍偏 **2.25°** —— 那部分是**常驻**污染（安装偏差 / 标度因数），**任何门控都救不了**，只能靠标定。

#### 3.8.2 出口是"两半"：`trust` 只是其中一半

`trust` 是**通道**不是**算法**（它只把"信不信"的决定权交出去）。真正难的是**判据**，而判据天然分居两层：

| 判据类型 | 需要的输入 | 只能在哪层做 | 通道 |
|---|---|---|---|
| **外部上下文型**<br>轮速 ωz vs gyro-z 对比、GPS 速度变化率、编码器抖动 | 需要**别的传感器** | **上层**（core 看不到轮子）| `trust` 形参 |
| **内部残差型**<br>`‖a×v̂‖`、与低通重力方向的偏差、马氏距离 | 需要 **q̂**（只有 solver 有） | **core 内** | 内部门控 |

```
上层（应用/平台）                      core（算法）
──────────────                        ──────────────
打滑检测 / 多源对比  ──trust──►  ┌─ 残差门控（内）
里程计质量评分                    │  trust 融合
                                 └─ ω += Kp·e·trust ...
```

> ⚠️ **必须避免的坑**：`trust` 若只会传 `1.0` 或 `0.0`，等于没有。"通道先行、判据后补"是有意为之（接口稳定后判据可迭代），但必须写进文档，否则会退化成"设计了却没人用"的空接口。

#### 3.8.3 打滑检测原理（麦轮小车）

**物理**：轮子转 ≠ 车按预期动 —— 空转打滑（轮转车没动）、滑移/抱死（车动轮没转够）。

**核心方法：用两个独立源测"同一个量"，比它们的差。**

```
主判据：  ω_odom  （4 轮速 → 逆运动学）       ← 里程计说车转多快
          ω_gyro  （IMU 直接测车体转动率）     ← 陀螺说车转多快
          residual = ω_odom − ω_gyro
          小 & 慢变  → 陀螺零偏（正常，量级 0.1°/s~1°/s）
          大 & 快变  → 打滑（或陀螺异常）
```

**四条可用判据（按性价比排序）**：

| # | 判据 | 原理 | 备注 |
|---|---|---|---|
| 1 | **ω_odom vs ω_gyro** | 同一物理量、两个独立测量 | **最干净**，首选 |
| 2 | **4 轮自洽性** | 麦轮 3 自由度 (vx,vy,ωz) 由 4 轮决定 → **超定** → 最小二乘残差 | 麦轮特有红利：冗余本身就是判据 |
| 3 | **里程计 dv/dt vs acc 水平分量** | 需要姿态解算结果 | 依赖 roll/pitch 精度，次选 |
| 4 | **零速检测** | 轮速≈0 + \|gyro\|≈0 + acc 方向稳定（三者组合）| ⚠️ **不能用 ‖a‖≈1g 单独判定**（见 §3.8.1）|

**麦轮特殊性（三条）**：
1. **横移时辊子效率低、滑移大** —— 麦轮的横向辊子摩擦损失明显高于纵向，横移与**原地旋转**是最容易打滑的工况；
2. **冗余可用** —— 4 轮 → 3 自由度，天然超定，判据 2 免费获得；
3. **打滑时陀螺通常是对的** —— IMU 测的是车体**真实**转动 → 打滑时应当**不信里程计**，而不是不信 IMU。（反向情形（陀螺饱和/失效）少见，但要保留该分支。）

**时间尺度**：打滑是**间歇性**的（转弯、加速、横移时）→ **`trust` 必须时变**，不能是一次性全局设定。

#### 3.8.4 统一载荷 + 按"数学形式"切分

**统一的是"可信度语义"，不是"入口类型"** —— 分三层（2026-09-12 精确化）：

| 层次 | 统一 or 专用 | 理由 |
|---|---|---|
| **core 门面入口** | **专用**（`observe` / `observe_heading`）| ① **编译期类型安全**：`observe_heading(acc)` 编译不过；统一载荷只能在运行时才发现 `kind_` 填错 ② 参数本就不同：acc 要 `dt` 做积分，yaw 纯 P **不要 `dt`**（Y5）③ 零开销（无 `kind_` 分派）|
| **可信度语义** | **统一**：每个入口都有 `trust` 形参 | `trust` / `age` 是**横切属性**，不该因源而异 |
| **外部仲裁器** | **统一载荷** | 它要处理**异构量测列表** —— 位置在 **core 之上**，**不是**门面入口 |

统一载荷（**位于 core 之上**的仲裁器用，非门面入口）：

```cpp
// core/measure/measurement.hpp（提案）
struct Measurement {
    enum class Kind : uint8_t { acc, mag, yaw, gyro, pose };
    Kind  kind_;
    float trust_;    // 0..1   ← 横切属性（§3.6.5 ②）
    float age_;      // 距上次有效多久（§3.6.5 ④）
    math::Vec3f vec_;   // 向量类载荷（acc / mag）
    float scalar_;      // 标量类载荷（yaw）
};
```

**切分维度必须按"数学形式"，不是按"传感器种类"**：

| 形式 | 量测 | `h(q̂)` | 残差 | 修正落点 |
|---|---|---|---|---|
| ① **向量观测** | acc、mag | `q̂*·r̂_w` | `m × h` | `ω += K·e` |
| ② **标量航向** | 里程计 / 编码器 / RTK | `ψ(q̂)` | `wrap(ref − ψ)` | `ω += K·e·v̂` |
| ③ **位姿 / 速度** | 视觉、GPS（EKF 阶段）| 复杂 | `z − h(x̂)` | `K·ν` |

**acc 与 mag 数学上完全同构**（只差常向量 `r̂_w`）→ 按传感器建类是**逐行重复的代码**。

**否决"虚基类 + 继承"方案**：
1. 违反 core 铁律（`AGENT.md`：禁 STL/异常/**RTTI**/动态内存）——vtable + 每条量测一次间接调用，在 1kHz 级热路径上无谓；
2. **多态解决不了真正的问题**：真正的难点是"该不该信**这一次**量测"，这是**横切所有源**的属性（trust / age / 卡方），**放不进任何单个源类**；
3. 本项目已有更快的多态（F13 模板策略）。

> `§4.3` 的 `measure/ # measurement.h gravity.h magnetometer.h yaw_reference.h` **即"按传感器切"**，应按上表改为 `vector_observation.h` / `heading_observation.h`（+ 未来的 `pose_observation.h`）。

### 3.9 目标平台约束与批次推进路线（2026-09-12 用户明确）

**主线应用：2.5D 四麦轮小车**（全向移动 + 平面/斜坡）。

```
硬件盘点：
  ✅ IMU 6 轴（acc + gyro）
  ✅ 4×轮编码器 → 里程计（逆运动学 → vx, vy, ωz）
  ❌ 磁力计（硬件空缺，大概率不上）

→ 两个源【都不可靠】：acc 被线性加速度污染（§3.8.1），里程计被麦轮打滑污染（§3.8.3）
→ 所以【仲裁是必需品，不是优化项】
```

**四个推论**：
1. **yaw 是主自由度**（2.5D 下 roll≈0，pitch 只有斜坡分量）→ 4a（yaw 注入）优先级最高 ✓
2. **唯一 yaw 基准是里程计** → 打滑时"没有第二意见"，这使 `trust` 的价值比通用场景更高
3. **暂不做 EKF 的理由成立**：小车等级不需要参考库 29.4µs 的算力；**先锁住 yaw 上车** 比追求算法完备更有价值
4. `§4.3` 的 `measure/` 切分需修正（见 §3.8.4）

**推进路线**：

```
                            小车能上车的最小闭环

 │
 ├─【4a-1】修 P0-4：is_meas_ 布尔闩锁 → 残差年龄计数器   ✅ 已落地（2026-09-12）
 │         （§3.6.5 ④ 的最小落地，也是 heading_age_ 的同一套机制）

 │         修掉 acc 通道的增益-速率耦合（τ 与量测速率无关）
 │
 ├─【4a′】上车实测（H7 + 真实麦轮里程计）        ★ 分水岭
```

| `Quat::normalize` 用位魔法 `inv_sqrt`（~4e-6）而 `Vec3::normalize` 用精确 `1/sqrt`（~6e-8） | 前者在 1kHz 级热路径上每帧跑，4e-6 模长误差 ≈ 2e-4° 姿态误差可忽略；两条路径不统一是**有意的**（原 P1-2） |
| `inv_sqrt` 对 0/负数的 float 路径不给 inf/nan | 位魔法固有；所有调用点均在受保护路径（`n2>0` / `n>0`）上 |
| 万向锁邻域 `to_euler` 精度 ~2e-4 rad | `asin` 在 ±1 附近导数发散，属公式固有，非实现缺陷 |
| `rotate` 快速展开式仅对单位四元数等于 `q v q*` | 已写入注释；这使 normalize 成为**正确性前提** |

### 4.4 核心接口（概念签名）

```cpp
namespace foucault {

template <typename Scalar = float, int DoF = 3>   // DoF: 1=2D, 3=3D(含2.5D)
class Estimator {
public:
    struct Config;                                // 噪声/增益/阈值/profile 预设

    void reset(const Config&);                    // 支持多实例，无全局状态
    void predict(Scalar dt, const Vec3<Scalar>& gyro);      // IMU 速率
    void observeAccel(const Vec3<Scalar>& accel, Scalar trust);   // 6轴
    void observeMag  (const Vec3<Scalar>& mag,   Scalar trust);   // 9轴
    void observeYaw  (Scalar heading_ref, Scalar trust);              // 外部真相源

    Quat<Scalar>        quaternion() const;
    void                euler(Scalar& roll, Scalar& pitch, Scalar& yaw) const;
    const OutputStatus& status() const;   // 收敛/降级/相对or绝对航向/innovation
};

struct GainSolver {                             // 可插拔（策略模式）
    virtual ~GainSolver() = default;
    virtual void reset() = 0;
    virtual void correct(State&, const Measurement&) = 0;
};

}
```
